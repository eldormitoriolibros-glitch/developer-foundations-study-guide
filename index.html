Five ideas every module repeats

  • Diagnose before you add. Each failure points to one missing structural piece: an output constraint, a tool-description exclusion, a pruning step, a deny rule. Rewording and adding length rarely fix anything.
  • Development hides production failures. Fixtures are 3–5× smaller than real tool output, sessions are short, traffic never hits a rate limit, and the only content the agent reads is content you wrote. Measure against the largest real input before shipping.
  • Enforce with structure, not with prose. Schemas over "please return JSON", hooks over CLAUDE.md lines, deny rules and least privilege over trusting the prompt. A prompt instruction is never a security control.
  • The eval is the gate. Model upgrades and downgrades, prompt changes, and version promotion all move on a measured score against a pinned baseline, changing one thing at a time.
  • Ask the worst-case question. "What is the worst outcome if this runs without a human check?" decides permission modes, HITL checkpoints, and where a seam needs a control.

Answering scenario questions

  • Read the constraint word first. "Most effective", "must never", "lowest cost", "no user waiting" or "reusable across apps" usually settles the answer before you read the options.
  • Watch for these distractors. All of them appear in the guide's samples and the course checkpoints:
    • "add a line to the prompt" when the question needs enforcement
    • "use a bigger or smaller model" for a problem that isn't about the model
    • "change the temperature" for anything that isn't sampling
    • "raise max_tokens" for a context problem
    • "retry" for a terminal error
    • "paste the data into context" when live, reusable access is needed
  • Pick the structural fix over the wording fix: schema over instruction, hook over CLAUDE.md, least privilege over trust, Batches over a loop.
  • For multiple-response items, select exactly the number asked for, and judge each option on its own merits.
  • Pace yourself. At about 2.3 minutes per item, mark long scenarios and come back to them rather than sinking five minutes in on the first pass.

Cheat sheet

Context window

  • Input already too large: validation error before generation.
  • Fits on input, hits the ceiling mid-output: partial output with stop_reason: model_context_window_exceeded.
  • Nothing is ever silently dropped; trimming or summarizing is the app's job.
  • API models: at least 200k tokens; newest flagships (Fable included) 1M by default.

Newest-model gotchas

  • Non-default temperature, top_p, top_k return a 400. Steer through prompting.
  • Thinking is adaptive, tuned with an effort setting. budget_tokens is deprecated and returns a 400.
  • Thinking content is omitted by default; request summarized display to show it.

stop_reason values

  • end_turn: finished, no action requested.
  • tool_use: run the tool calls and send results.
  • max_tokens: truncated, may be mid-structure.
  • refusal: HTTP 200, but fail fast and log.
  • model_context_window_exceeded: ran out of window.

Error classes

  • Retriable: 429 rate limit, 529 overloaded, 500 502 503 504, most timeouts.
  • Terminal: 400 401 403 404.
  • Honor retry-after; otherwise exponential backoff with jitter and a cap.
  • When unsure, treat it as terminal. The SDK already retries transient errors, so don't stack loops.

Message Batches API

  • Up to 100,000 requests or 256 MB per batch.
  • Submit, get batch_id, poll, download. Up to 24 h.
  • About 50% cheaper per token (confirm at build time).
  • Results come back unordered: match on custom_id.

Prompt caching

  • cache_control: {type: "ephemeral"} on the last block to cache; up to 4 breakpoints, or automatic mode.
  • Order processed: tools → system → messages.
  • TTL 5 min, refreshed on each hit; ttl: "1h" opt-in.
  • Writes 1.25× (5 min) or 2× (1 h); reads 0.1×.
  • Exact prefix match; minimum about 1,024 tokens on most models.

Structured outputs

  • JSON outputs: output_config.format with type json_schema.
  • Strict tool use: strict: true on the tool definition.
  • First call on a new schema is slower; the grammar is cached 24 h.
  • Adds input tokens, can't be combined with prefill, and you still check for refusal and max_tokens.

Images and files

  • Image tokens ≈ ⌈w/28⌉ × ⌈h/28⌉. 1000×1000 ≈ 1,296.
  • One-off: inline base64. Reused: Files API file_id (beta, not on Bedrock/Vertex). Public stable URL: URL source.
  • PDFs use a document block; title and context are optional.

Beta headers named in the course

  • MCP connector: mcp-client-2025-11-20
  • Managed Agents: managed-agents-2026-04-01
  • Skills on the API: code-execution-2025-08-25 + skills-2025-10-02

Claude Code settings

  • User ~/.claude/settings.json · Project .claude/settings.json · Local .claude/settings.local.json (git-ignored) · Enterprise managed-settings.json.
  • Deny beats allow in every mode. An enterprise deny can't be overridden.
  • Hooks: PreToolUse exit code 2 blocks; precedence deny > ask > allow.

MCP placement

  • stdio = local subprocess. Streamable HTTP = remote/shared. SSE = legacy.
  • Local scope ~/.claude.json · User · Project .mcp.json · Enterprise managed.
  • The API connector only reaches remote HTTP servers.
  • Secrets: ${ENV_VAR} references, never inline.

Compliance routing

  • Managed Agents sessions live server-side: not ZDR or HIPAA BAA eligible.
  • Direct API has no EU data residency; use Bedrock or Vertex with the region pinned.
  • FedRAMP: Claude for Government (High), Bedrock GovCloud (High, IL4/5), Vertex Assured Workloads. AWS Marketplace Enterprise is not.
  • ZDR eligibility varies by model and platform.

Numbers worth remembering

  • Orchestrator-worker ≈ 15× the tokens of a chat.
  • Production tool output ≈ 3–5× test fixtures.
  • Tool descriptions: 3–4 sentences, including when not to use.
  • CLAUDE.md starts to dilute past about 200–300 lines.
  • Claude Code loads MCP tools upfront only under about 10% of the window (opt-in).

Model choice

  • Tiers: Fable (most capable) · Opus · Sonnet (default) · Haiku (speed/cost).
  • Start on Sonnet. Go up only when an eval shows a miss; go down only when an eval shows the drop is acceptable.
  • Pin full IDs. From Claude 4.6, the ID alone pins a snapshot; older models need the date suffix.

Mechanisms, drawn

MSO Foundations

Module 1 · 57 min

The vocabulary the rest of the path assumes: what you are paying for, why the same prompt answers differently, which levers are independent, and how requests reach the model.

Tokens and the context budget

  • Everything is counted in tokens: system prompt, history, tool definitions, tool results and the response. Tokens are both the billing unit and the window's unit.
  • Characters-per-token depends on the model's tokenizer and changes between generations, so treat any rule of thumb as model-specific.
  • The window is a fixed budget holding the whole request at once. It rarely fills in development and fills fast in production.

Sampling and non-determinism

  • At each step the model samples the next token from a probability distribution. Low temperature concentrates it and high temperature spreads it out.
  • Temperature 0 makes runs more repeatable but never guarantees identical output. On the newest models, sampling parameters can't be changed at all.
  • Consequence for testing: never assert exact text. Assert properties (a field exists, a value is in range, it parses) and use a model-graded eval for meaning.

Two independent levers

LeverWhat it setsRule
Model choiceWhich family member runs: Fable, Opus, Sonnet, HaikuStart on Sonnet; move up or down only on eval evidence.
Reasoning modeWhether and how deeply the model thinks, per request (adaptive thinking + effort)Pays off on hard multi-step work; wasted on lookups and classification.
Prompting modeZero-shot, one-shot, or multi-shot (few-shot) examplesAdd examples when the output's shape, casing or edge case keeps missing. One or two examples often beat another paragraph of instructions.

These levers interact: a stronger model may succeed zero-shot where a smaller one needs examples, and examples can let a cheaper model do the job. Try the smallest model with the fewest examples that pass your eval.

Production-Grade Prompting, Agents & Tool Use

Module 2 · 209 min

This is the largest module. Every topic is framed as a failure that testing misses and production exposes, paired with the implementation decision that prevents it.

  • You can take few-shot examples from your highest-scoring eval outputs.
  • Don't stack all four techniques on a simple job: "summarize this paragraph" needs neither examples nor a schema.
Production trap · the prompt that grew longer

Six revisions each added description and none added the missing constraint. Along the way the verbose prompt produced verbose output (over 2,000 characters per call) and latency went up with no accuracy gain, because the model matches its length and style to the input. The fix was a JSON schema and two examples. If three re-prompts in a row fail, stop adding text and diagnose.

Structured outputs: moving the format into the API

A prompt asks for a format; constrained decoding enforces it. JSON outputs (output_config.format, type json_schema) constrain the final response. Strict tool use (strict: true) validates the arguments Claude passes to a tool. The costs: a slower first call while the grammar compiles (cached 24 h), a few injected input tokens, no prefill, and responses that still won't match on refusal or max_tokens.

Carry-back rule

In tool-use conversations, every thinking block (redacted ones included) goes back to the API unchanged on the next turn. Each block is signed; editing, summarizing or dropping it gets the request rejected. Thinking tokens are billed as output tokens.

Tool use and schema design

Claude never runs your tools. The loop: you define tools → Claude replies with a tool_use block (name, id, input) and stop_reason: tool_use → your code executes → you send a tool_result with the same id in a new request → Claude continues or ends the turn. The model is stateless between calls.

BlockRule your code must follow
textWhen it comes alongside tool_use, keep the full content array in history.
tool_useAnswer it in the immediately following user turn. Resolve every tool_use from one turn together.
tool_resultSent in the user role. tool_use_id must match exactly (matching is by id, not position). Set is_error: true on failure.
thinkingReturn it unchanged.
  • Name: specific (get_account_balance, not get_data).
  • Description: 3–4 sentences covering what it does, when to use it, when not to, and what it returns. Claude routes mostly on name plus description; parameter types are a secondary signal.
  • Required vs. optional: mark a field required only when the call makes no sense without it. Requiring everything forces Claude to invent values.
  • Dependencies: dependent calls go in separate turns. Independent calls can run in parallel in one turn, which current models do by default; disable_parallel_tool_use forces one call per turn.
  • If two tools need ever-longer descriptions to stay apart, merge them into one tool with a type parameter.
  • Exclusion conditions such as "only if X was already called" rely on the full history being sent. Truncate history and they silently stop working.

MCP instead of writing schemas yourself

  • The loop doesn't change. The client sends ListToolsRequest and hands the definitions to Claude.
  • Connected servers' definitions use context even when idle. With the API connector, use mcp_toolset with default_config and per-tool configs: defer_loading and enabled.
  • Transports: stdio for local servers, Streamable HTTP for remote (SSE-only is deprecated). The API connector supports only remote HTTP servers.
  • Use both: an MCP server for breadth, an allowlist to narrow it, and tuned descriptions for the tools you actually route to.

Production trap · the dropped stream

A handler appended the turn whenever its read loop ended. A network blip cut a tool_use block mid-JSON, and the retry failed validation, so the team spent an afternoon debugging the schema. A loop ending is not a message completing. Gate the append on message_stop, discard partial turns, and retry from the last complete turn.

if stop_seen:
    messages.append({"role": "assistant", "content": assemble(blocks)})
else:
    raise StreamInterruptedError("partial turn discarded; retry from last complete turn")

Model selection and cost

  • Defaulting to the most capable model is the most common and most expensive mistake. A higher tier can still come out cheaper if it reaches the answer in fewer tokens, and the cost of a wrong answer belongs in the calculation.
  • Routing: send most traffic to a default model and override it on a cheap signal such as task type, input length or a difficulty label. Pin a single model when traffic is uniform.
  • Instrument every call for input/output tokens, latency and error rate. One step often accounts for about 90% of spend.
  • Levers: model choice, prompt and context size, number of tool calls, streaming (perceived latency), batching (cost), caching (repeated prefixes). Batching and caching stack.
  • Caching only pays when the prefix is identical (even adding "please" breaks it), recurs within the TTL, clears the minimum length, and can tolerate being briefly stale.
Orchestrator-worker as a hiring decision

A lead plans the work, subagents explore in parallel in their own contexts, and the lead synthesizes. Anthropic's research setup (Opus 4 lead, Sonnet 4 workers) beat a single Opus 4 agent but used about 15× the tokens of a chat, so a 10k-token question becomes about 150k. Token usage explains most of the performance gain. It suits broad, independent research and not tightly coupled work like coding. Use a strong lead with cheaper workers, and give every worker its own retry handling.

Reliability floor first. Fix the latency ceiling and retry budget (for example 4 s and 3 retries), then optimize cost above them. A pinned baseline eval score is how you enforce the floor.

Security

  • Prompt injection: the model reads its context as one stream with no built-in line between your instructions and fetched text. Any content someone else can write is a vector (pages, shared docs, DB records, email, tool output), including content planted for later or hidden in white text or images.
  • Delimiters are a soft boundary, and training plus classifiers lower the odds without guaranteeing anything. The boundary you can rely on is what the agent is allowed to do.
  • Jailbreak means bypassing the model's safety constraints; injection means hijacking your app's instructions. Both get the same defense: constrain the input and limit the actions.
  • Least privilege decides how bad a steered agent can be. Narrow write paths and explicit denies (/etc, /secrets, ~/.aws) turn an injection into a denied action and a log line. Anything that can edit the agent's auth config is as privileged as the secret itself.
  • Hooks enforce; prompts don't. A PreToolUse hook returns permissionDecision: "deny" and writes an audit entry. Precedence is deny > ask > allow.
  • OS-level sandboxing, with the filesystem limited to the working directory and the network to named endpoints, holds even where no hook or rule covers a path. Enterprise reviewers ask about it first.
  • Regulated scoping: be ready to explain data residency, audit logging and managed configuration, and confirm ZDR eligibility for each model and platform.

Accessing Claude with the API

  • Always go through your own server. The API key must never ship in client-side code. The flow runs client → your server → Anthropic API → model → back the same way.
  • Every request needs an API key, model, messages and max_tokens. max_tokens is a safety cap, not a target length. Official SDKs exist for Python, TypeScript/JavaScript, Go and Ruby.
  • Inside the model: tokenize → embed (numbers that capture meaning) → contextualize (refine each token by its neighbors) → generate one token at a time, mixing probability with controlled randomness.
  • Generation stops at max_tokens, a natural end-of-sequence token, or a stop sequence. The response carries the content, usage (input and output tokens) and stop_reason.
  • The API is stateless. Keep the message list yourself and send the full history every turn; otherwise "write another sentence" has nothing to refer to.
  • System prompts go in the system= parameter. Include it only when it's set, because the API rejects system=None.
  • Streaming: pass stream=True for raw events, or use client.messages.stream(...) with stream.text_stream for text only. stream.get_final_message() returns the assembled message for storage.

  • Code shape: run_prompt(case) → run_test_case returns output, case and score → run_eval(dataset) averages the scores.

  • Results go back as a user message of tool_result blocks (tool_use_id, string content, is_error), one per tool call. Send the tools list again on the follow-up request.
  • The loop: call Claude → append → stop if stop_reason != "tool_use" → run every requested tool (catch exceptions as is_error: true) → append the results → repeat. A small router maps tool names to functions. Adding a tool means writing the function and schema, then registering both in the list and the router.
  • Streaming tool arguments: input_json events carry partial_json and a running snapshot. By default the API buffers until each top-level key is complete and valid, so output arrives in bursts. Fine-grained tool calling turns that validation off: chunks arrive faster, but your code must survive invalid JSON.

Retrieval-augmented generation

Stuffing a whole document into the prompt hits length limits, works less well on very long prompts, and costs more and runs slower. RAG chunks the document ahead of time and sends only the relevant chunks. The cost is a preprocessing step, a search mechanism, and the risk that a chunk lacks context.

ChunkingTrade-off
Size-based (+ overlap)Cuts words and context, but works on anything, including code. The usual production default
Structure-based (split on headers)The cleanest chunks, but only when you control the formatting
Sentence-based (+ overlap)A practical middle ground
SemanticThe most relevant chunks, but the most expensive and complex
  • Embeddings are lists of numbers (each −1 to 1) whose individual dimensions can't be interpreted. Anthropic doesn't offer an embedding model; the course uses VoyageAI.
  • Flow: chunk → embed → normalize → store in a vector DB together with the original text → embed the query → nearest neighbors → prompt with the chunks in XML tags.
  • Cosine similarity ranges from −1 to 1, and closer to 1 means more similar. Cosine distance = 1 − similarity, so lower means more similar.
  • BM25 lexical search weights rare terms highly, which catches exact IDs like INC-2023-Q4-011 that semantic search can miss.
  • Hybrid retrieval merges the two rankings with reciprocal rank fusion: RRF(d) = Σ 1 / (k + rank_i(d)), where k is often 60.

Platform features

  • Extended thinking: turn it on only after prompt work has stalled on your evals. Signatures prevent tampering; redacted blocks come back encrypted (flagged by safety systems) and must be passed through as-is.
  • Images: up to 100 per request, 5 MB each, max 8000 px for a single image or 2000 px when sending several, as base64 or a URL. Use the same prompting craft as with text, such as a step-by-step counting method with a second check, or a one-shot example image.
  • PDFs: a document block with application/pdf. Claude reads text, images, charts and tables.
  • Citations: add "title" and "citations": {"enabled": true} to a document block. Responses then include cited_text, the document index and title, and page numbers (character positions for plain-text sources).
  • Prompt caching: put cache_control: {"type": "ephemeral"} on a longhand block. Everything up to and including that block is cached and must match exactly. Breakpoints work on system prompts, the last tool, images and tool blocks. Processing order is tools → system → messages, with up to 4 breakpoints and a 1,024-token minimum. Check usage for cache_creation_input_tokens (a write) vs. cache_read_input_tokens (a read).

Building with MCP

  • MCP isn't "just tool use". It changes who writes and maintains the tools: an MCP server wraps a service (such as GitHub) so you don't have to. Real projects usually build either a client or a server, not both.
  • Messages: ListToolsRequest/Result and CallToolRequest/Result. Your server fetches the tool list through the client, sends it to Claude, and runs Claude's tool calls through the client.
  • Python SDK: FastMCP("DocumentMCP"), plus @mcp.tool(name, description) with Pydantic Field(description=…), which generates the schema for you.
  • Inspector: mcp dev mcp_server.py opens a browser UI for testing tools, resources and prompts without a full app.
  • Client: wrap the SDK's ClientSession so it cleans up after itself, and expose list_tools(), call_tool(), read_resource(), list_prompts() and get_prompt().

Claude Code, workflows and agents

  • Claude Code: /init writes CLAUDE.md, which can be project-level (shared), local (personal, not in git) or user-level (all projects). /clear resets context, and claude mcp add <name> <command> connects a server.
  • The most effective loop: feed it the relevant files → ask for a plan (no code yet) → implement. For TDD: context → brainstorm test cases → write the tests → write code until they pass.
  • Agents need abstract, combinable tools. Claude Code has bash, read, write, edit, glob and grep, not a "refactor" tool. A good agent also asks for missing inputs, like the purchase date before calculating a warranty expiry.
  • Environment inspection: ask "How will Claude know this action worked?" That means screenshots after UI actions, reading a file before editing it, and checking generated output (for example, captions or frame grabs of a rendered video).

Workflows vs. agents

Workflows are more accurate, easier to test and more predictable, but less flexible and more work to design. Agents handle novel tasks and can ask users for input, but complete tasks less reliably and are harder to evaluate. The course's advice: build workflows wherever you can, and use agents only when the task truly calls for one.

Build checklist

  1. Server: mcp = FastMCP("DocumentMCP"), with your data in memory.
  2. Tools: @mcp.tool(name=…, description=…) on a typed function, with arguments described by Pydantic Field(description=…). The SDK writes the JSON schema. Raise ValueError for bad input so Claude can see the error.
  3. Test: mcp dev mcp_server.py opens the Inspector in your browser (a local URL such as 127.0.0.1:6274). Connect, list tools, run them, and check resources and prompts.
  4. Client: wrap the SDK's ClientSession in your own class so it cleans up, and implement list_tools() and call_tool().
  5. Resources: use @mcp.resource("docs://documents", mime_type="application/json") for a direct resource, or "docs://documents/{doc_id}" for a templated one whose parameter becomes a function argument. The client calls read_resource(AnyUrl(uri)), takes contents[0], and parses it by MIME type.
  6. Prompts: @mcp.prompt(name, description) returns a list of messages (base.UserMessage). The client calls list_prompts() and get_prompt(name, args), and the CLI shows them as / commands.

Model Context Protocol: Advanced Topics

Supporting course · about 1.1 hours · 15 lessons

This course covers the parts of MCP where the server reaches back to the client (sampling, notifications, roots), the JSON messages underneath, and why moving from stdio to Streamable HTTP can silently switch those features off. The walkthrough videos and the assessment have no written content, so they aren't summarized here.

Sampling: the server borrows the client's model

  • A server that needs text generation, such as summarizing the Wikipedia pages it fetched, asks the client to call Claude for it instead of holding its own API key.
  • Benefits: a simpler server, no credentials on the server, and the client pays for the tokens. That makes sampling the right choice for public servers, which shouldn't run up AI costs for every user.
  • Server side: await ctx.session.create_message(messages=[SamplingMessage(...)], max_tokens=…, system_prompt=…). Client side: pass a sampling_callback to ClientSession that calls Claude and returns a CreateMessageResult.

Log and progress notifications

  • For long-running tools, the server reports what it's doing through the injected Context: await context.info("…") for log lines and await context.report_progress(20, 100) for progress.
  • On the client, logging_callback goes on the ClientSession, and progress_callback goes on each call_tool().
  • How you present them is up to you: print them in a CLI, push them over WebSockets, SSE or polling on the web, or drive progress bars on desktop. They're optional and purely for the user's benefit.

Roots: which folders a server may touch

  • Roots tell a server which files and folders it may use. Claude can then call list_roots and look through those directories, so "convert biking.mp4" works without the user typing a full path.
  • They also set a boundary: grant Desktop only, and Documents and Downloads stay off-limits. Requests outside the roots should return an error that Claude can explain to the user.
Watch out · the SDK doesn't enforce roots

You have to write the check yourself, typically an is_path_allowed(path) helper that compares the requested path against the approved roots. Call it in every tool that touches files, before the operation runs.

JSON message types

  • The authoritative list is the MCP specification repository, separate from the SDKs. It's written in TypeScript purely as a way to describe the data types.
  • Request → Result pairs: Initialize, CallTool, ListPrompts, ReadResource and so on. Notifications are one-way, with no reply: Progress, LoggingMessage, ToolListChanged, ResourceUpdated.
  • The protocol is bidirectional: servers send requests to clients too (CreateMessage for sampling, ListRoots). That's what makes the choice of transport matter.

Transports

TransportHow it worksLimits
stdioThe client launches the server as a subprocess; the client writes to stdin and the server writes to stdout. Either side can send at any timeSame machine only. It's the "ideal" baseline, and you can test a server by pasting JSON into the terminal

  • Handshake on every connection: Initialize Request → Initialize Result (the server's capabilities) → Initialized Notification. No other request is allowed before it.
  • A tool call opens a second SSE stream. The primary GET stream stays open for server-initiated requests and carries progress notifications. A per-call stream carries log messages and the tool result, then closes.

Hands-on labs

The exam guide recommends building at least one Claude application that uses the API, one or more tools, some prompt and context engineering, and basic security and evals. These seven labs cover that, each in about an hour, in Python or TypeScript. Each gives the goal, the steps, and a "done when" check. There are no full solutions: hitting the traps yourself is how they stick.

1 · A tool-use loop from scratch

D2 · D8 · M2 · P1

Goal: a raw Messages API loop with two tools, get_current_datetime and add_duration.

  1. Write both schemas, each description with a when-to-use and a when-not-to-use sentence.
  2. Loop while stop_reason == "tool_use". Append the full assistant content, then all tool_results in one user message.
  3. Wrap execution in try/except and return is_error: true with the message.
  4. Log every turn's ids.

Done when: "What day is it 103 days from today?" chains both tools; a forced exception makes Claude react instead of answering wrongly; and your log shows each tool_use id matched in the next turn.

2 · A stream handler that survives a drop

D2 · M2

Goal: stream a tool-using response and assemble it safely.

  1. Collect blocks by index, adding input_json_delta fragments to each.
  2. Parse tool input only at content_block_stop, and append to history only after message_stop.
  3. Simulate a drop by breaking out of the event loop after a few deltas.

Done when: a simulated drop raises, leaves history unchanged, and a retry from the last complete turn succeeds. Then remove the guard and watch the next request fail validation.

3 · A small eval harness

D4 · D6 · M4 · P1

Goal: define "done" for an extraction prompt as a score.

  1. Write 10 cases, 3 of them edge cases (two dates, no date, a relative date), each with an expected output.
  2. Add a code grader (parse + required fields) and a model grader that returns strengths, weaknesses, reasoning and a score.
  3. Hand-label 5 outputs and measure how often the judge agrees with you.
  4. Change one thing in the prompt, then re-run.

Done when: you have a recorded baseline, one measured change with a per-case diff, and a judge-agreement number.

4 · A retry wrapper that doesn't make things worse

D2 · D4 · M4

Goal: one place that decides retriable vs. terminal.

  1. Retry 429, 529 and 5xx; fail fast on 400, 401, 403 and 404.
  2. Honor retry-after; otherwise use exponential backoff with jitter and a cap.
  3. Raise on stop_reason: "refusal".
  4. Decide whether the SDK's own retries stay on, so you never stack two retry loops.

Done when: a faked series of 429s shows growing waits and stops at the cap, a faked 400 raises at once, and a refusal never retries.

5 · Measure prompt caching

D5 · M4 · P1

Goal: see caching work, and see it break.

  1. Use count_tokens to confirm your system prompt is above the minimum (~1,024 tokens).
  2. Put cache_control: {type: "ephemeral"} on it and send two requests.
  3. Change one character and send again, then wait past the TTL and send again.

Done when: usage shows cache_creation_input_tokens on the first call, cache_read_input_tokens on the second, a miss after the one-character change, and a miss after the TTL.

6 · An MCP server with all three primitives

D8 · P2 · P3 · M3

Goal: a FastMCP server with one tool, a direct and a templated resource, and one prompt.

  1. Test it in the Inspector (mcp dev server.py).
  2. Add context.report_progress() to the tool.
  3. Connect it to Claude Code with claude mcp add.
  4. Run it over Streamable HTTP, then turn on stateless_http.

Done when: the Inspector lists all three primitives, Claude Code calls the tool, and you've seen progress updates disappear when stateless_http is on.

7 · A guardrail hook in Claude Code

D3 · D7 · M3 · M4

Goal: make "never read .env*" an enforced rule, not a convention.

  1. Add a PreToolUse hook with a matcher for Read, Edit and Write. It inspects the path, exits with code 2 and writes the reason to stderr.
  2. Add a PostToolUse hook that appends each call to an audit log.
  3. Add a deny rule in .claude/settings.json as a second layer.

Done when: asking Claude to read .env is blocked with your reason shown, the attempt appears in the log, and removing the hook still leaves the deny rule blocking it.

Glossary

Accelerator
A build packaged so the next engagement configures it: parameters, documented assumptions, a bundled eval.
Agent SDK
The agent loop behind Claude Code, as a library (claude-agent-sdk, @anthropic-ai/claude-agent-sdk). Unlike the Anthropic SDK, which is a thin API wrapper, it runs the loop.
Agentic search
The model issues its own queries over several rounds instead of using a pre-built index. No staleness, but more tokens per query.
Compaction
Summarizing history to free context. Only what the summarizer keeps survives.
Context window
The fixed token budget for one request: prompt, history, tools, results and output.
Eval
Cases, expected behaviors and grades that define "done" as a score.
Exponential backoff
Growing, capped waits with jitter between retries; honors retry-after when present.
HITL
A human approval step before a consequential or irreversible action.
Hook
A script bound to a Claude Code lifecycle event. It runs every time, unlike a CLAUDE.md instruction.
Integration test
A test of the handoff between two components, where most silent failures hide.
LLM-as-judge
A second model grading open-ended output with a rubric. Trustworthy only once calibrated against human labels.
MCP
Model Context Protocol: servers expose tools, resources and prompts to any MCP client.
Orchestrator-worker
A lead agent fans work out to parallel subagents and synthesizes the results, at about 15× the tokens.
Pinned model ID
A fixed model snapshot, as opposed to an alias that moves.
Prompt injection
Instructions hidden in content the agent reads, then followed as if they were commands.
Retriable vs. terminal
Whether retrying the identical request could plausibly succeed.
Rules file
A .claude/rules/ file that loads only for matching paths.
Skill
A SKILL.md procedure loaded on demand when its description matches.
Subagent
An isolated context that returns a summary. It doesn't inherit history or skills, but does inherit permissions.
Trust boundary
A seam where data crosses between components or environments and needs its own control.
